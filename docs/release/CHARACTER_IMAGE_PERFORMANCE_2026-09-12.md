# キャラクター画像操作の性能

## 判定

通常配布物cc160e7b、0.25 CPU/512 MiBで、約1.1MBのJPEGは対象5操作のp95が3秒以内だった。一方、許可範囲内の約4.5MBでは画像追加7.098秒・一覧3.485秒で未達。両試験500要求ずつはすべて期待結果に一致し、予期しないエラー0。軽い画像だけの成功を画像機能全体の合格に拡張しない。

## 条件

- 登録100人・同時10フロー、6版/7版を各50人。各人は他者と独立した非公開キャラクターを使用。
- 非公開グループ100、キャラクター/シナリオ/セッション各1,000の新規データ。各グループには所有者と別ユーザーが参加し、利用者の総数は100人。
- 所有者による画像追加、一覧、別ユーザーの一覧拒否、所有者による削除、空一覧確認を順に実行。各操作100件、版ごとに250件。
- Token認証のHTTP開始から本文の読み取りまでを測定し、nearest-rank法のp95を使用。人間の操作間隔は挿入しない。合成JPEGの生成時間は測定に含めない。
- 標準Dockerイメージ `tableno-release:cc160e7b`、本番設定、ファイル保存はローカル。内部専用Dockerネットワーク、PG18.3（2 CPU/1 GiB）、Redis7（128 MiB）。DB/Redisは使い捨てtmpfs、実AWS・S3・外部サービスへ接続しない。
- ソース差し替えなし。各試験は新規DBから開始し、専用資源の所有ラベルを照合して終了後削除。継続費用の変更なし。

## 0.25 CPU/512 MiBの結果

| 操作 | 1024×1536、1,138,638 bytesのp95秒 | 2048×3072、4,553,465 bytesのp95秒 |
| --- | --- | --- |
| 画像追加 | 2.931 | 7.098 |
| 画像一覧 | 1.495 | 3.485 |
| 他者の一覧拒否（期待404） | 1.406 | 2.298 |
| 画像削除 | 1.521 | 2.308 |
| 空一覧確認 | 1.306 | 2.005 |

画像追加は201・先頭順序0・メイン画像フラグ・画像URLの存在、一覧は保存したIDだけが1件、削除は204・空本文・再取得0件を検査した。画像ファイル自体のダウンロード・デコード・ハッシュ一致や、既存画像4枚への5枚目追加は、この測定の検証範囲に含めていない。

## 証跡と残課題

### 0.5 CPU/1 GiBとの比較

同じcc160e7b、2048×3072・4,553,465 bytesのJPEG、登録100人・同時10フローを新規DBで測定し、500要求すべて期待結果に一致、エラー0。p95は画像追加3.652秒、一覧1.278秒、他者一覧拒否1.189秒、削除1.285秒、空一覧確認0.982秒。画像追加は改善したが3秒基準には未達であり、この資源構成を採用すれば合格とは言えない。

CPUとメモリを同時に増やしたため、改善をCPUだけの効果とは断定しない。CPU制限の計測ファイル `/sys/fs/cgroup/cpu.stat` が存在せず、最初の試行は画像操作前に中止・資源削除した。その環境依存の計測だけを外した新規試行で上記結果を取得したため、CPUスロットリングやピークメモリは未測定。証跡は `tmp/large-image-halfcpu-r2-cc160e7b/`、中止記録は `tmp/large-image-halfcpu-cc160e7b/`。いずれも専用資源は削除済み。

Git管理外の `tmp/image-performance-cc160e7b/image-results.json` と `tmp/large-image-performance-cc160e7b/image-results.json` に全要求の時間・版・成否、同ディレクトリに試験スクリプトとログを保存。アプリの起動・種データ作成は集計外。

画像追加のソース確認では再圧縮・縮小処理は見当たらないが、これだけでCPU不足や遅延箇所を断定しない。資源量の比較と実行時プロファイル、実S3、既存画像あり、長時間負荷、実ブラウザの送信・描画時間を含む確認が残る。画像サイズ制限や機能を変更して合格扱いにはしない。

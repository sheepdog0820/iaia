# 複数の返金・異議申し立てによる停止理由の保持

## 問題と変更

既存処理は利用者ごとに最後の停止理由を1つ保持していた。異議申し立ての勝訴でこの理由を解除すると、別件の係争中・敗訴・返金による停止も消えてプレミアムが復旧した。3つの回帰テストで再現してから修正した。

勝訴時の復旧条件に、同じ利用者のStripe監査履歴に他の自動停止理由が残っていないことを追加した。異議申し立てはIDごとの最後の処理結果で判定し、勝訴以外が残る場合は停止を維持する。返金による停止も保持する。自動停止が無効だった通知は情報として扱う。停止対象のIDが不足した履歴は、自動復旧の根拠として扱わない。

対象は最後にStripe権限の付与・復旧が完了した後の停止履歴。それ以前にレビューされて解消された停止理由まで永久に持ち越さない。最初の回帰実行では、既存のオフラインsmokeが「返金をレビューして復旧してから次の異議申し立て」を模擬していたため失敗した。この復旧境界を実装し、専用の回帰テストでも確認した。手動プレミアムの優先、現在購読の照会、解約後に復旧しない制限は維持した。

## 確認結果

- 課金・法務・本番設定・権限連携の268テスト成功（24.025秒）。
- 新規の回帰は、別件係争中、敗訴、返金、すべて勝訴、以前の停止解消、自動停止なし、履歴不足を確認。さらにIDなしの勝訴と情報のみの異議申し立てを加え、8テストの個別実行が成功（0.162秒）。coverage JSONで新規判定関数に未実行行がないことを確認した。すべての分岐・運用条件の証明ではない。
- 使い捨てPostgreSQL 18.3で13テスト成功（3.880秒）。同じ顧客の2件の勝訴を別接続から同時に処理し、両件解消後に権限が有効となり、復旧監査と購読照会が各1回であることを確認。既存の同時購入・請求更新の試験も通過。
- 実サンドボックス `acct_1UFA5iE2s31mT3or` に専用顧客を作成し、公式テストPaymentMethodで2件の異議申し立てを発生させた。winning_evidenceを順に送信し、1件目は権限停止のまま、2件目は権限復旧、復旧監査は1件となった。受信イベントは全件succeeded。11項目成功。[実証跡](STRIPE_MULTIPLE_REVOCATION_EVENTS_2026-09-19.json)を参照。

実試験では複数の停止理由を作るため、サンドボックスのAPIから同一顧客にテスト購読を2件作成した。通常のアプリ購入の二重契約防止を解除したものではない。実カード・実課金・実メールは使用せず、使い捨てSQLiteとlocalhost受信器を使用した。終了時に2件とも解約し、HTTP/CLI転送を停止、DBを破棄した。PostgreSQLコンテナも今回専用のものを停止した。

Black/isort・flake8・Bandit・差分検査を通過。新しい利用者向け文言はない。前候補f5d9acbaのCIは途中確認で4ジョブ成功、単体/統合とブラウザが実行中だった。今回の修正のCI結果とは区別する。

## 限界と反映条件

判定は受信・保存済みの監査履歴に基づく。同じ異議申し立ての古いcreated通知がwonの後に届く場合など、Stripeの最新Dispute状態との照合は本記録時点では追加対応が必要だった。[後続修正・実試験](STRIPE_DISPUTE_ORDERING_2026-09-19.md)で対応済み。未受信イベント、履歴欠損、手動修復の全組合せを証明していない。メール配送保証、AWSでの実接続と有料必須ゲートも未完了で、正式公開はNo-Go。

この変更自体に追加マイグレーションはない。同じ候補の0065・0066は共有DBへ未適用。main/AWS、Secrets、料金、税設定、継続費用は変更していない。コードを戻すと複数停止理由の誤解除が再発するため、切戻しは課金停止を前提とする。監査履歴を削除して復旧する運用は行わない。

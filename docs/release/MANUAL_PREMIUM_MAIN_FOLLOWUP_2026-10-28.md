# ユーザー編集・手動付与と課金更新の整合性（2026-10-28）

## 対象

正式公開はNo-Goを維持する。[管理者の3操作を修正したPR #12](https://github.com/sheepdog0820/iaia/pull/12)のhead `63e01667df14b9aa38bfac093ab5fda0a11f0b5b` を基点に、別ブランチ `codex/manual-premium-followups-20261028` で既知の `f543f784` から製品差分と回帰試験だけを選んだ。対象はユーザー編集の `CustomUserAdmin.save_model` と `set_premium_user`。保留中の後続全体やStripe SDK/APIの更新は含めない。

一覧・フォーム/コマンドの最初の取得後に購入・Webhook・削除が進むと、古い `is_premium` や他の未編集項目を上書きする。監査保存の失敗でユーザーや権限だけが残ることもある。この問題を隔離DBで再現した。実ユーザーの権限を変更する操作は行っていない。

## 修正

- プロフィールだけの編集はユーザーをロックし、現在の権限を保持して、実際に編集した具体的な列だけ保存する。関連付けだけの編集で古いプロフィールや権限を書き戻さず、変更していないチェック欄を手動の付与/停止意図として扱わない。
- 権限を明示的に変更する場合と手動コマンドは、共通helperで課金行→ユーザーの順にロックする。初回購入で課金行を同時作成する場合も同じ一意制約・共有行で待機し、現在のフラグを読んでから変更と監査を同じtransactionに保存する。
- 古い手動付与に変更がなく、直列化用の課金行を初めて作っただけなら、その空の行は残さない。再照合が新たな無効課金レコードとして旧付与を失効させないためで、既存のStripeのID・状態・課金行を削除/変更する処理ではない。
- 新規ユーザー作成を含め、監査失敗時はユーザー/権限と新しい直列化用行をrollbackする。削除済みの対象を復活させず、管理画面は日本語の404、コマンドは日本語のCommandErrorにして成功出力を行わない。
- 既存の手動付与方針、変更なしの繰り返しで監査を増やさない扱い、理由・actor・source、メールによる対象検索、グループ等の保存と管理画面の権限チェックを保持する。PGのCI対象へ回帰ファイルを追加する。

DBスキーマ/移行、料金、実Stripe操作、Secrets/IAM/OAuth、外部通知・常設資源・費用は変更しない。管理者が意図して行う付与/停止の方針や権限境界は広げない。課金レコード自体の編集画面での古い保存は別の後続対象であり、この修正で全管理者経路を完了とはしない。

## 承認と復旧

# 開発AWS Web容量増強の承認案

## 目的と根拠

候補bb61b0e6の[隔離測定](CHARACTER_IMAGE_PERFORMANCE_BB61B0E6_2026-09-19.md)で、登録100人・同時10人、4.55 MB画像の追加p95は現行相当0.25 CPU/512 MiBで6.957秒、1 CPU/2 GiBで1.776秒だった。現行相当では削除も3.094秒で基準未達。両試験500要求は内容一致・エラー0。画像の画質・サイズ上限・権限制御は変更していない。

1 CPU/2 GiBへの増強を開発環境での次の検証構成として推奨する。ローカルの単発測定であり、実AWSや全操作の性能保証ではない。CPUとメモリの個別寄与も確定していない。

## 変更範囲

- AWSアカウント083773015316、東京、既存ECS `tableno-aws-pre` のWebサービス1台。
- [別のアプリ反映案](STRIPE_AWS_APP_APPROVAL_2026-09-19.md)のbb61b0e6とDB0065〜0067反映が承認・成功した後、稼働定義のCPUを256から1024、メモリを512から2048へ変更したリビジョンを登録し、既存Webサービスを更新する。
- イメージ、台数1、Secrets参照、IAM、ネットワーク、購入・配送の無効設定は維持する。常設worker/beat/Redisの追加費用とは別。
- 反映前に稼働リビジョンと設定差分を保存し、未知の変更があれば停止する。Terraform stateの古いWeb定義を使った全体applyは行わない。
- 更新後に稼働台数、rollout、readiness、主要画面を確認する。実ユーザーや共有DBを使う負荷試験はこの容量変更だけでは承認されたものと扱わず、専用データ・操作・後片付けを具体化する。

アプリ反映案を承認しただけでこの増強が承認されたとは扱わない。逆に、この容量増強の承認だけでmainマージ・共有DB変更を実行しない。両方が揃った範囲で順次進める。

## 切戻しと残条件

増強後の不健全化や依頼による切戻しは、増強直前の同じアプリ版・旧容量の定義へ戻す。台数を増やさず、DBの逆マイグレーションやデータ削除はしない。bb61b0e6のアプリ反映自体が失敗した場合の旧版49への切戻しは別のアプリ反映案に従う。

現在は未実行。価格・対象・効果の限定条件を示した承認用資料である。正式公開には実AWSでの性能、Stripe設定と課金フロー、メール・監視、外部連携、復旧、OS指摘等の残条件も必要。

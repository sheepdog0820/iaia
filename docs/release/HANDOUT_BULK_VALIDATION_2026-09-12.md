# ハンドアウト一括作成の入力形式検査

## 不具合と修正

GM向け `/api/schedules/gm-handouts/bulk_create/` で `handouts` にnull・数値・真偽値を渡すと、反復処理でTypeErrorとなり500応答になる不具合を隔離テストで再現した。文字列・辞書も配列として誤処理され、入力形式を説明する応答になっていなかった。

GM権限の確認後、作成処理に入る前に配列であることを検査し、不正な型は日本語の400応答で拒否する。配列内の不正な項目に返す英語メッセージも日本語へ変更した。正常な項目の作成と不正な項目のエラーを併記する既存の部分成功は維持する。

## 検証範囲

修正後は新規2テストと既存の書き込み権限・管理テストを合わせて26件成功（37.528秒）。使い捨てSQLiteを使用し、既存DBは変更していない。Black/isort/flake8/Banditと日本語文言・差分を確認した。既存管理テストには404/405を許容するケースもあるため、26件成功を全管理ルートの成功へ拡張しない。今回の新規テストは実際のGM APIに対して応答と保存結果を厳密に検査する。

新規テストで5種類の不正な型、400応答の文言、DBへの書き込みがないことを確認する。正常な項目とnullを混在させた配列では、201応答・作成1件・エラー1件・保存内容・日本語エラーを検査する。修正前は2テストで1失敗・5エラーを再現した。

実稼働DB・AWS・Secrets・料金・権限設定の変更はない。アプリ側の既存GM権限検査を維持し、DBマイグレーションは不要。main・AWS反映、修正候補の全CI、ブラウザからの一括作成は別途確認する。修正をrevertすると不正入力の500応答が再発するが、直前のハンドアウト更新・削除の権限修正は維持できる。

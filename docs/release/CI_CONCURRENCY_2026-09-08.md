# 最新コミットのCI待機を減らす設定

2026-09-08、GitHub ActionsのAPIで最新30実行を確認。直近の8実行がqueued、先行する8実行がin_progressだった。同じ変更にpush/PRの両実行があり、数分間隔の文書更新でも5ジョブずつ起動していた。アカウントの同時実行枠やGitHub内部の待機原因までは確認していない。

## 変更

Django CIにworkflow名とgithub.refの組み合わせでconcurrencyを設定し、cancel-in-progressを有効にした。[GitHub公式仕様](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)に基づき、同じブランチまたは同じPRの新しい実行が古い実行を置き換える。

pushのrefs/headsとPRのrefs/pullは異なるため、両者を相互にキャンセルしない。別ブランチや別workflowもグループが異なる。mainもCIのみの最新実行を優先する。テスト項目、ジョブ数、トリガー、デプロイ構成は変更しない。

この設定を持たずに開始された既存実行が遡って整理されるとは保証しない。既存runの手動キャンセル・再実行はしていない。中断された旧コミットを成功扱いせず、マージ判断には対象の最新SHAで必要なジョブが完了した証拠を使う。

## 検証と残事項

YAMLの構文と設定値、既存5ジョブが維持されることを確認し、差分・UTF-8/LFを検証した。実GitHubでの新旧実行の置換は、後続実行時に確認する。設定だけで待機が解消したとは報告しない。

PostgreSQL 18.3変更d12c0c08のpush run 34194811572、PR run 34194814714は調査時queuedで合格未確認。直近f7930fa0もqueuedだった。過去bc69f587のPR run 34193275629はplaywrightジョブ101955539471が失敗している。同SHAのpushと後続50433a89/654a4dd7の両イベントはsuccessだが、過去の失敗原因を確定したわけではない。失敗ステップはブラウザ導入とE2E実行の複合ステップであり、ログ未確認の段階では環境障害やテスト不具合のどちらとも断定しない。

DB・Secrets・実環境・権限の変更や新規契約はない。CI設定はこのconcurrency節を戻せば復旧できる。既にキャンセルされた実行の再開は別途必要になる。

## 過去Firefox失敗のログ・trace調査

同日、job 101955539471のログとartifact 10043364765を取得した。ローカル取得先はGit管理外の `tmp/guest-firefox-ci.zip`。ブラウザ導入失敗ではなく、regular-user-session.spec.tsの匿名ゲスト参加・通常登録者への引継ぎテストがFirefoxで30秒のテスト制限に達した。停止位置はguest.gotoのload待ち。最終結果は185 passed / 1 flakyで、再試行成功をfailOnFlakyTestsが失敗扱いにした。再試行や失敗判定を緩める変更はしていない。

該当リクエストのアプリログはページ本体とローカルCSS/JS/fontに200を記録し、traceでも確認した。ゲストのナビゲーションはテストの登録処理開始から数秒で始まっているため、単に登録処理だけで30秒を使い切ったとの判断はできない。

ゲストcontextのtraceにはGoogle FontsのCSSとgstaticのInter/Poppinsへの通信があり、共通 `static/css/arkham_modern.css` 冒頭の外部@importと一致する。テンプレートだけの外部URL検索では見落とす依存だった。また413件のFont Awesome警告が記録されていた。ただしフォント応答も200で、traceのtime=0やtimings=-1だけからネットワーク停止を断定しない。これらがタイムアウトの直接原因かは未確定。

次は外部フォントに依存しない配信方法を検討し、外部通信を遮断した状態でゲスト参加・引継ぎの全操作を検証する。修正時はフォントのライセンス・表示差・既存静的資材の配信確認も行う。今回の調査だけでアプリの遅延を修正済み、またはCI全体成功とは判定しない。

## 外部フォント遮断時のゲストフロー検証

2026-09-08、ae4e33fbのgit archiveを専用の `tmp/offline-guest-candidate` に展開し、既存のPlaywright 1.63ブラウザイメージで検証した。ネットワークはnone、公開ポートなし。Djangoとブラウザは同じコンテナのlocalhostを使用し、空SQLiteから合成データを作成。元リポジトリや実DBをアプリの書き込み先にしなかった。

試験コピー内で通常ページと追加guestContextの両方にfonts.googleapis.com/fonts.gstatic.comをabortするrouteを加えた。アプリコード、30秒の既定制限時間、操作・期待値は変更せず、対象を匿名ゲスト参加から通常登録ユーザーへの引継ぎテスト1件に限定、再試行0で3ブラウザを実行した。外部ドメインを検出した遮断ログは計24件。

Chromium/Firefox/WebKitの3件すべて成功、合計1.2分、終了0。招待発行、匿名参加、招待再利用410、未認証の引継ぎ拒否、通常登録、不正/空コード拒否、正しい引継ぎ、再引継ぎ409とセッション参照まで通った。コンテナは終了時に削除され、所有ラベルのリソース残存なしを確認。証跡はGit管理外の `tmp/offline-guest-run.log`、試験コピー内のoffline.config.tsと修正したspec。

初回準備はローカルPython 3.11.1がtarfile.extractallのfilter引数に対応せず失敗し、テストを開始できなかった。git archiveの各要素が専用展開先内で、シンボリックリンク/ハードリンクでないことを確認する手順へ変更して再実行した。元アーカイブや既存成果物は削除していない。

これは外部フォントが即座に失敗する場合の機能継続の証拠である。通信が保留される場合、フォントの表示差、元CIの遅延の直接原因は未検証。外部依存そのものはアプリに残っている。アプリ修正済み・CI合格とはせず、自己配信の検討と遅延条件の検証を継続する。

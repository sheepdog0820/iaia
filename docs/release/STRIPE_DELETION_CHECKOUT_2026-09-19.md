# 購入画面・未着通知を考慮した退会処理

## 問題と変更

ローカルの契約状態だけでは、開いたままのCheckoutや決済後に未着のWebhookを検知できない。退会すると、利用者は決済可能な購入画面を残したり、既に開始した契約の管理先を失ったりする。5回帰テストでこれらの保護がないことを再現した。

退会時はCheckout作成と同じ購読行をロックし、削除まで保持する。課金履歴がない場合も同じ行を確保する。作成APIの結果が不明な記録は削除せず、再試行用キーを残す。

顧客IDがある場合、追跡済みCheckoutと旧版が残した購入画面を照合し、未完了の画面を失効させる。完了済みCheckoutに紐付く契約、保存済み契約、顧客の契約一覧をStripeで確認してから退会する。顧客や参照IDの不一致・未知の状態・API障害・購入画面の失効失敗では、退会を拒否してログインとデータを保持する。例外の内部情報は利用者に表示しない。

Stripeの[Checkout失効API](https://docs.stripe.com/api/checkout/sessions/expire)は、失効後の購入完了を防ぐ。失効と決済完了が競合しAPIが失敗した場合も削除しない。途中で退会が拒否されても、既に失効した購入画面は戻さない。再購入する場合は課金画面で新たに開始する。

## 検証

- 使い捨てPostgreSQL 18.3で認証・課金・退会・並行処理の243テスト成功（11.705秒）。退会がロックを保持している間に購入を開始し、アカウント削除後にCheckout作成APIを呼ばないことを確認した。
- 新しい課金退会モジュール72実行行はcoverage 100%。全分岐やすべての並行実行順序の網羅を意味しない。
- 実Stripeサンドボックスで6項目成功。[結果JSON](STRIPE_DELETION_API_2026-09-19.json)。追跡済み購入画面を失効してから隔離アカウントを削除し、Stripe側のexpired状態を再取得した。別の試験では、ローカルへの通知反映なしで試用契約を作成し、退会拒否を確認。サンドボックスで契約を解約後、退会可能になった。
- 実API試験の2購入画面は失効済み、1試用契約は解約済み。隔離DBを破棄し、PostgreSQLコンテナも停止・削除した。実課金・外部メール送信なし。
- Black/isort、flake8、Bandit、UTF-8/LF・差分検査を実施。利用者に表示するエラーは日本語で、API例外文は含めない。

# Google再試行の受付時権限確認

## 問題と修正

失敗したCalendar/Sheetsジョブの再試行APIは、所有者と失敗状態を確認していたが、Google連携の有効設定・認可範囲を確認せず新しいジョブを作成していた。Calendarでは同期対象の閲覧権限を失っていても同期状態をPENDINGへ変更していた。

Googleジョブの再試行を受け付ける前に、アカウント有効・各連携ON・必要scopeを確認し、不足時は日本語400応答で拒否する。Calendarは共通のセッションアクセス判定も行い、権限不足では同期状態・前回エラーを変更しない。実行時のworkerによる再確認は維持する。

変更前もworkerに権限確認があったため、今回の再現だけで権限のない外部送信が起きたとは判定しない。受付時の不要なジョブ作成と状態変更を防ぐ修正である。

## 検証と範囲

- 変更前に、Calendar/Sheets各3状態（連携なし・OFF・scopeなし）とCalendar閲覧権限失効の計7ケースが期待に反することを再現。
- f16eb72bの配布イメージに新しいテストだけを読み込んだ再現でも7ケース失敗。修正ソースも読み込んだ場合は関連25テストすべて成功。
- 拒否時の日本語エラー、新規ジョブなし、キュー呼出しなし、Calendarの元状態・エラー保持を検証。正しい権限を持つ既存の再試行成功ケースも通過。
- Docker試験は外部通信なし・使い捨てメモリDB・ダミー設定。外部キューはモックで、Google実送信0件。終了時にコンテナを削除。
- Black/isort/flake8、差分、日本語文言を確認。証跡はGit管理外の `tmp/google-retry-runtime-red.log` と `tmp/google-retry-green.log`。

DB移行・共有データ変更・IAM/Secrets・課金変更なし。既存の過去ジョブは変更しない。全体CIと開発AWS反映はこの修正時点では未完了。実Googleの取消・更新・再試行や常設基盤の検証を代替しない。前版へ戻すと受付時の検査も戻るため、復旧時も実行側の権限確認を維持する。

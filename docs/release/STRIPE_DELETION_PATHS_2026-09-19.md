# ユーザー削除API・管理画面の課金確認統一

退会画面に追加した課金確認が、通常ユーザーAPI・管理者API・Django管理画面の単件/一括削除を通らない問題を確認した。契約が残る利用者や、Checkout作成結果が不明な利用者を、これらの入口から削除できた。

## 修正

- 通常ユーザーAPIと管理者APIの削除処理を、既存の共通退会サービスへ接続した。課金確認で拒否された場合は、日本語の理由を含むHTTP 400を返す。対象者の取得と権限制限は従来のまま。
- Django管理画面の単件削除も同じサービスを使用し、拒否時には一覧へ戻って日本語のエラーを表示する。
- 管理画面の一括削除ではPK順に処理し、1件でも拒否されたら選択全体をロールバックする。削除前に記録される管理ログも同じトランザクションに含め、削除していない利用者の削除ログを残さない。
- 無料利用者の削除と、通常利用者から他人・管理者APIへのアクセス拒否を維持した。

一括処理の途中で失効済みになったStripe購入画面はDBロールバックで復活しない。利用者は残り、必要なら課金画面から購入を再開する。複数利用者の削除ではStripe照会も人数分発生するため、操作時間に注意が必要。

## 検証

修正前に新しい9テスト中5件の失敗を確認した。修正後は使い捨てPostgreSQL 18.3で、認証・課金・退会・同時処理を含む252テスト成功（12.890秒）。APIの実URLと、管理画面への確認POST・一括アクション・リダイレクト後の日本語表示をDjango Clientで確認した。ブラウザーによる管理画面操作の確認ではない。

coverageでは追加した管理画面メソッド18実行行とAPI共通処理5実行行の未実行行は0。Black/isort、flake8、Bandit、差分・UTF-8/LF検査に合格。隔離PostgreSQLコンテナは停止・削除済み。

通常画面のブラウザー検証や実StripeのAPI・署名付き通知検証は[先行検証](STRIPE_DELETION_BROWSER_2026-09-19.md)、[同時処理検証](STRIPE_DELETION_RACE_2026-09-19.md)を参照。後続の[4削除経路と実Stripeの接続試験](STRIPE_DELETION_PATHS_API_2026-09-19.md)は23項目成功した。新経路の管理画面を実ブラウザーで操作する試験とAWS上の検証は残る。

## 反映

追加DBマイグレーション・Secrets・権限付与・継続費用の変更はない。main・AWSは変更していない。以前の候補0f6b81feとそのコンテナには本修正が含まれないため、正式な反映候補ではこの修正を取り込み、変更後CI・パッケージを確認する。既存の承認対象を無断で差し替えない。

共通サービスを使わない任意の管理スクリプトや直接SQLによる削除まで防ぐDB制約は追加していない。実データを削除する運用では承認を取り、同じ課金確認を利用する。切戻すと削除経路の保護が外れるため、課金・ユーザー削除を制限して判断する。正式公開は引き続きNo-Go。

# 日程調整の二重確定と失敗時の復旧

2026-09-08、作業ブランチ272ed4bfからの変更。受け入れ条件F03の競合を調査し、日程確定の2件の不具合を再現・修正した。

## 再現と修正

確定APIは読み取り時点のis_closedだけを検査していた。先行要求が確定した後も、取得済みの古いオブジェクトを使う後続要求は200となり、別セッションを作成できた。また、確定済みフラグの保存とセッション作成が別々に行われ、セッション作成失敗後に投票だけが閉じたまま残った。

新規回帰テストで、古いオブジェクトを返す後続API要求と、セッション作成例外を再現。変更前はいずれも失敗した。実時間に依存する待機やテストの再試行は加えていない。

DatePoll.confirm_dateをトランザクション化し、投票行のロック取得後に締切状態を再確認する。既に閉じている要求は日本語の400応答とする。ロック保持中にDBの現在値を読み直し、日程保存・セッション作成/更新・関連付けをまとめて確定する。失敗時はDB変更全体を戻し、再試行できる状態を維持する。

## 検証

- 隔離SQLite: 新規テストは変更前2失敗/1スキップ。変更後は高度な日程調整・キャッシュ検査を含め24成功/1スキップ（21.341秒）。
- 隔離PostgreSQL 16: 同じ25件すべて成功（23.748秒）。2接続が異なる候補と同じ未確定投票を読み終えてから同時確定し、成功1件・締切拒否1件、セッション1件、投票とセッションの日付一致を確認した。lock_timeoutは5秒、同期待ちは10秒で制限。
- SQLiteのスキップは行ロックを要する並行試験であり、SQLiteの同時書き込み成功を証明しない。
- 既存セッションの日付・主開催日時更新、通常確定、再確定拒否、作成者以外の拒否を既存テストで確認。
- 変更したPython3ファイルのBlack/isort/Flake8と差分検査が成功。重要な日本語の締切メッセージは回帰テストで確認。

テスト用イメージtableno-full:01a52f52に現行schedulesディレクトリだけを読み取り専用で重ね、ENV_FILE空・合成資格情報で実行した。PGは専用internalネットワークの空DBであり、共有DBや実ユーザーデータを使用していない。これは現行候補全体の再ビルド・全体検証ではなく、変更に対する対象検証である。

## 影響と残条件

スキーマ・Secrets・料金・外部サービス設定の変更はない。行ロックは確定処理の間だけ保持する。既存データに過去の二重セッションがあるかは調査しておらず、実データの修復も行わない。取り消す場合はこの変更をrevertできるが、二重確定と失敗時の不整合が再発する。

F03全体の完了ではない。投票・候補追加・通常PATCHとの競合、参加権限の変更、異なる投票から同じセッションへの確定などは別の未確認条件として残る。

# ブラウザテストの開発ログインと文書読み込み

## 問題の切り分け

[CI実行34020134852](https://github.com/sheepdog0820/iaia/actions/runs/34020134852)のWebKitでは、開発ログイン後のセッション一覧への遷移が30秒でタイムアウトした。APIクライアント側のログインPOSTとリダイレクトは302/200で成功し、ブラウザ側の一覧GETは完了していなかった。記録とハッシュは [登録テスト調査](BROWSER_SIGNUP_INPUT_2026-09-06.md) に残している。

共通の `devLogin` は初期画面の `commit` だけを待ち、ユーザーカードが表示されると文書読み込みが完了していなくても認証POSTと次の遷移を開始していた。`commit` はレスポンスを受けて文書の読み込みを開始した時点であり、DOMContentLoadedとは異なる（[Playwright公式API](https://playwright.dev/docs/api/class-page#page-goto)）。

一時診断で、ユーザーカードの後に置いたスクリプト応答を1秒遅延させ、認証処理を開始した時点の `document.readyState` を記録した。旧ヘルパーは3ブラウザとも `loading` のまま認証処理を開始した。これは読み込み順序の問題を証明するが、元のCIタイムアウトを同じ条件で再現したものではない。

## 変更と検証

最初の `page.goto` でDOMContentLoadedを待つようにし、失敗時に同じ画面へ再遷移する内部リトライを除いた。タイムアウト、認証方法、遷移先、失敗判定は維持する。アプリのログイン処理や実ユーザー認証は変更しない。

同じ遅延診断は変更後3ブラウザで成功（8.8秒）。診断だけはAPI POSTをスタブ化し、開始時の状態を測定した。実ログインの成功を示すものではないため、通常の実アプリE2E全体を別途実行する。

診断ソースは `tmp/dev-login-readiness-probe.spec.ts`、設定は `tmp/dev-login-readiness.config.ts`、結果は `tmp/dev-login-readiness-{red,green}.log` と各出力ディレクトリ。全体検証は `tmp/dev-login-full.log` と `tmp/dev-login-full-output/results.json` に保存する。

キャッシュ済みブラウザイメージに現在の全フローテスト・ビュー修正2ファイル・共通テンプレート・Axios・設定を重ねた隔離コンテナーで、空のSQLiteと合成ユーザーを使う。再試行は0。実サービス・実ユーザーデータには触れない。

## 限界

全体実行は185成功・1失敗（15.6分、再試行なし）で終了1。Firefoxの `google-settings-save.spec.ts` の通信エラー試験で、保存クリック後もメッセージが空のままだった。トレースにGoogle設定PUTは記録されていない。クリックは不安定な要素の待機を経て完了扱いとなっていたが、実際の保存開始に至った証拠はない。`tmp/google-save-network-full-failure.trace.zip` に保存した。

この時点では失敗を成功扱いにせず、ヘルパー変更は未コミットのまま保持して原因調査を継続した。保存ハンドラーの登録は初期読み込み要求より先に実施されており、ハンドラー未登録を原因とは判断できない。

トレースのDOMスナップショットを復元すると、クリック直前のスクロール位置は0、クリック後は116、直後の検証開始時は180、5秒後は682だった。保存ボタンのクリック位置は画面座標 (127, 700)。クリック後もスクロールが進行していた証拠はあるが、押下・解放の対象要素は未記録のため、クリック不成立の直接原因までは確定していない。BootstrapのCSSに `prefers-reduced-motion: no-preference` 時の `scroll-behavior: smooth` がある。根拠なく全画面のアニメーションを変更したり、保存を再クリックして成功扱いにしたりせず、切り分けを継続する。

コミット済み `c9801e6c` の [CI実行34021021856](https://github.com/sheepdog0820/iaia/actions/runs/34021021856) は全5ジョブ成功を確認した。このCIには未コミットのヘルパー変更は含まれないため、変更後の全体検証の代わりにはしない。

追加診断では一時コピーのテストに `pointerdown/up`、`mousedown/up`、`click`、`focusin`、`scroll/scrollend` の記録を加え、対象ID・座標・スクロール位置・保存ボタンの矩形だけを添付した。通常クリック10回は10成功（50.5秒）、押下から解放まで150msのクリック3回も3成功（17.5秒）。いずれもFirefox、再試行0、隔離DB、通信エラー後の再保存まで確認した。

通常クリックの成功例でも後からスクロール位置が約680になるものがあり、スクロールの発生そのものは失敗の十分条件ではない。また診断時のボタン高さは約44.4pxで、失敗トレースの約38.4pxとは異なる。元の失敗の押下・解放イベントは記録していないため、追加診断をもって原因確定や全体失敗の解消とはしない。

一時診断ソースは `tmp/prepare-google-pointer-probe.py` と生成先 `tmp/google-pointer-probe.spec.ts`。結果とイベント添付は `tmp/google-pointer-probe-output/results.json` と `tmp/google-pointer-delay-output/results.json`、ログは各同名の `.log` に保存した。製品CSSや保存ハンドラーは変更していない。

その後、YouTubeのドラッグ診断でスクロール中の座標ずれを再現し、共通CSSの自動スクロール指定を修正した（[検証記録](BROWSER_SCROLL_INTERACTIONS_2026-09-06.md)）。このCSS変更と現在の開発ログイン補助処理を含む関連検証は30件成功（3ブラウザ、再試行なし）。全体検証を `tmp/interaction-full-validation-output/results.json` に別途記録する。元のGoogle失敗を、原因まで同一と証明したものではない。

後続の全体実行は185成功・1失敗（16.2分）で、開発ログインの失敗はなかった。Firefoxのセッション作成でタイトルが空のままだった失敗は [別のテスト修正](SCENARIO_MODAL_READINESS_2026-09-06.md) を行い、関連する6件が成功した。全体実行の失敗記録と修正後の対象検証を区別し、更新後の全体CIを確認する。

読み込み順序の改善をもってWebKitの入力欠落・ページ遷移タイムアウトをすべて解消済みとはしない。最新CIと、再発時の診断添付を確認する。復旧はテストヘルパー変更のrevertで行い、アプリやDBの復旧は不要。

# Google処理途中の再接続を検知して追加送信を停止（2026-10-06）

## 対象と修正

- 親コミット: `cfc515ce3e2f141f7f682bef020f40179ae84f01`。ブランチ: `codex/google-connection-guard-20261006`。
- Calendar/Sheetsの既存送信前認可チェックは、同じscopeと有効フラグを保ったGoogle再接続を区別できなかった。取得済みの古いaccess tokenを、再接続後の次の送信にも使っていた。
- worker開始時に連携行のID/`connected_at`を保持し、各HTTP直前にDBから取得した連携と比較する。同一Googleアカウントの再認可、別Googleアカウントへの接続、同じ日時の連携行再作成を検知する。資格情報/UIDはジョブへ保存しない。
- 接続変更は日本語の固定エラーでジョブを失敗として完了し、追加HTTP/自動retryをしない。Sheetsは送信済み分の進捗（試験の201行中100行では49）を保持し、途中まで出力された可能性を付記する。Calendarは同期状態/エラーも記録し、外部予定IDを勝手に消さない。
- 認可を失った場合の既存エラー/終了値を維持する。接続変更だけの場合は`connection-changed`を返す。Calendarの全6 HTTP箇所に同じチェックを通す。
- レビューで、設定保存PUTも`connected_at`を更新していることを確認した。これは再接続の区別に使えず、同じ設定の保存でも中断を起こすため、設定PUTは既存の接続日時を保持するよう修正した。新規作成時のモデル既定値とOAuth接続時の日時更新は維持する。
- 通常のtoken refreshは接続変更にしない。最後のHTTPが受理された後に接続が変更されたケースは、既存の成功結果を巻き戻さない。HTTP中にDBロック/トランザクションを追加しない。新規テストを既存PG CIに追加する。

- PostgreSQL 18.3の隔離DB: 同じ101件が成功（36.767秒、省略0）。今回のケースは順序を決めた接続変更であり、既存のPGロック競合試験も回帰として実行したが、HTTP送信直前の任意の競合が原子的に止まる証拠ではない。
- 最終差分の本体34実行文/14分岐、新規テスト210文/38分岐が100%。worker全体/Google実通信の100%網羅を意味しない。

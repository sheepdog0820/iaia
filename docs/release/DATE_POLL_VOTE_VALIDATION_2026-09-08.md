# 日程投票の不正入力と一括保存の検証

2026-09-08、作業ブランチd6c1945aからの修正。日程投票APIがrequest.dataを直接保存していたため、入力型・選択肢・文字数の検証が欠けていた。

## 再現した問題

- 本文が配列、votesが文字列、投票要素がnull/数値、option_idが不正文字列の場合に500。
- status/commentがnullの場合にDB制約違反で500。未定義のstatusと101文字のコメントはSQLiteで保存できた。
- 別の投票の候補IDを含めても黙ってスキップし、先行する有効な回答だけを更新して200を返した。

新規4テストの変更前実行では10条件が失敗。正常な選択肢・境界値のケースは成功した。検証データは隔離DB内の合成データのみ。

## 修正内容

本文形式を確認し、専用入力シリアライザで全投票の候補ID、モデル定義の3種類のstatus、100文字以内のcommentを検証してから保存する。status省略時available、comment省略時空文字の挙動と、コメントの空白保持は維持する。

対象投票に存在しない候補IDは400にする。既存のトランザクション内で例外を返すため、有効な回答の更新後に不正候補が見つかっても全体を戻す。候補の存在を他の投票まで検索して応答で区別する処理は追加しない。

## 検証結果と影響

- SQLite: 投票入力・作成・確定・編集権限・高度な日程調整・キャッシュの48件で43成功/5スキップ（22.442秒）。
- PostgreSQL 16: 同じ48件すべて成功（52.330秒）。スキップされた並行試験5件も成功。
- 不正入力は400で保存なし。別投票の候補が混ざった一括回答では、元の回答状態・コメント・件数が維持される。
- available/maybe/unavailable、100文字、既定値の保存を確認。新規テストをCIのproduction-databaseにも追加した。
- 変更したPython3ファイルのBlack/isort/Flake8、差分・日本語表示のレビューに成功。入力型と候補不存在の独自メッセージは日本語、フィールド検証は既存の日本語ロケール設定を使用する。

既存検証イメージtableno-full:01a52f52に現行schedulesを読み取り専用で重ね、ENV_FILE空・合成資格情報で検証した。候補全体の再ビルド・全体CIの成功を表す結果ではない。専用PGとinternalネットワークは所有ラベル確認後に削除済み。共有環境、スキーマ、実データ、Secrets、料金は変更していない。

過去に保存された不正な回答は未調査・未修復。取り消す場合は本修正をrevertできるが、不正入力の500と不正値・一部回答だけの保存が再発する。正式公開条件全体の完了は[受け入れ表](FORMAL_RELEASE_ACCEPTANCE_MATRIX.md)で別途判断する。

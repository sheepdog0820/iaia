# Calendar作成応答の喪失と再試行の重複防止

## 問題と変更

予定の新規作成はGoogleによる自動採番を使い、成功応答のIDを受け取ってから同期記録へ保存していた。Google側では保存に成功したのに応答だけが失われると、次の試行でも新規作成となり、模擬APIで予定が2件に増えることを再現した。

新規作成時は同期記録のID・所有者・セッション・作成日時を基にUUIDv5の16進表記を生成して予定IDに指定する。同じ同期記録なら別ジョブで再試行してもIDを維持する。同期記録を作り直した場合は作成日時等が変わるため別IDになる。既にexternal_event_idを保存済みの連携は従来のIDを使う。

作成が409の場合、そのIDの予定を取得し、IDと非公開のタブレノ同期情報を照合する。一致した場合だけ同じ予定を現在のセッション内容で更新する。不一致は日本語の失敗として止め、別のIDで再作成したり、無関係な予定を上書きしたりしない。

## 仕様の根拠

Googleはアプリ側のイベントID指定を、バックエンドで作成成功後に失敗した場合の重複防止として案内している。[予定作成ガイド](https://developers.google.com/workspace/calendar/api/guides/create-events)

IDはbase32hex文字・5〜1024文字・カレンダー内一意が条件で、UUIDアルゴリズムの使用を推奨している。今回の32文字の16進UUIDは文字・長さの条件を満たす。Googleの分散システムがあらゆる衝突を検出する保証はないため、実環境での挙動確認は別途必要。[Events.insert](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert)

409 duplicateは同じIDの予定が存在する状態であり、同じ予定を扱う場合は更新を使う。[エラー処理ガイド](https://developers.google.com/workspace/calendar/api/guides/errors)

## 検証と残条件

- 修正前、保存成功直後のTimeoutと別ジョブの再試行で模擬予定が2件になることを再現。
- 修正後、同じ条件で1件、両試行のID一致、ID書式、再試行前に変更したタイトルの反映、同期記録・ジョブの成功を確認。
- 409から取得した予定のID不一致、IDは一致するが同期情報なしの場合、FAILEDとなり外部ID未保存・更新呼出しなし。
- 既存の作成成功テストは実APIの契約に合わせて指定IDを返す模擬応答へ変更。1回の作成確認だけだった旧テスト名の「idempotently」も修正し、新しい応答喪失テストと区別。
- 関連30テスト成功後、同期情報なしの追加ケースを含む3配送テストが成功。通常イメージ202b1e3dへ変更ソース/テストを読み込んで実行。外部通信なし、使い捨てDB、Google APIはモック、実送信0件。
- Black/isort/flake8・差分・日本語エラーを確認。証跡はGit管理外の `tmp/calendar-idempotency-red.log`、`tmp/calendar-idempotency-green.log`、`tmp/calendar-idempotency-conflict-green.log`。

DB移行・既存同期記録の一括変更・権限/Secrets・課金変更なし。過去の自動採番で応答を失った予定や既に存在する重複は、この変更だけでは自動照合・削除しない。全体CI、通常配布物への組込み、開発AWS反映、実Googleでの通信断・同時実行・取消/再開を含む検証は未完了。正式公開の合格をこの模擬試験だけで判定しない。

## 全体CIで判明した既存テストの修正

5da23e35のpush CI（34444065768）は6項目中5項目が成功し、Unit / Integrationで既存の認可統合テスト1件が失敗した。模擬応答が指定した予定IDと無関係な固定IDを返していたため、新しいID照合で失敗していた。Googleの作成応答と同様にリクエストのIDを返すようテストを修正し、過去の自動採番IDを保存済みの予定は新規作成せず従来のIDで更新する確認も追加した。アプリ実装は変更していない。

通常イメージ5da23e35に修正テストのみを読み込み、認可統合・外部連携・非同期ジョブ・Calendar配送の35テストが成功。外部通信なし、使い捨てDBで実施。全体CIは修正コミットで再確認する。AWSは595a390a／タスク定義47のままで、この失敗した候補のデプロイは実行していない。

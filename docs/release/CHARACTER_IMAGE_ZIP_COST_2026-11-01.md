# 画像ZIPの再圧縮コストと失敗ログ保護

PR60の固定head `2ca0f211`を親にした別ブランチで、画像ZIP取得のCPU負荷とstorage失敗時のログを修正する。PR60のhead・mainマージ確認や、固定3de/image4617のコピー内5移行リハーサル確認は変更しない。全25条件と正式公開No-Goを維持する。

## 変更と利用者への影響

JPEG/PNG/GIFと保存済みWebPのsignatureを持つ画像は、ZIP内で再圧縮を省く候補とする。拡張子からは判定しない。64 KiBを超える場合は、先頭64 KiBをlevel1で試し圧縮し、5%を超えて縮むなら従来どおりDEFLATEする。低圧縮率で保存した大きなPNG等が、無条件のSTOREで大きくなる回帰を実PNGで再現してから、この条件を追加した。未知形式・不完全signatureはDEFLATEを維持する。

保存済み画像を再エンコードせず、展開後の全bytes・ZIP名/順序・同名回避・添付headerを維持する。新しいアップロード形式を許可する変更ではない。小さな画像や試料以外に圧縮可能な領域がある画像では、ZIPが以前より大きくなる場合がある。試料は圧縮効果の推定であり、全画像でサイズが小さくなる保証ではない。全主要操作の性能条件を達成した結果へ広げない。

storageの読込失敗では、WARNINGの固定文だけを記録し、私有ファイル名・例外本文・tracebackを記録しない。失敗画像を飛ばす挙動と、全画像を取得できなければ404とする挙動は維持する。ZIP取得の認証・共有範囲・版別データ取得、画像数・容量の上限は変更しない。

## 調査・再現と検証

変更前の通常image `sha256:d651e19610d52bc97d236e1920ef2c8027c767d951d36c621062737a8f31cc91`をネットワークなし・0.25 CPU/128 MiBで使い、既存性能試験と同じ4,553,465 bytesの合成JPEGについて10回ずつ測定した。DEFLATEの中央値はwall0.491秒・CPU0.118秒、STOREはwall0.00248秒・CPU0.00217秒。ZIPはそれぞれ4,553,695/4,553,603 bytesで、STOREの方が92 bytes小さかった。各ZIPから展開した全bytesの一致を確認した。これは圧縮部分の比較であり、HTTP応答全体や新しい試料判定を含む最終配布物の実測ではない。

最初の回帰では、形式5条件の圧縮method、不要なdeflater生成、失敗ログの7失敗を確認した。新しい8テストは、上記に加えて実際の低圧縮PNGの有用な圧縮、large高entropy画像、未知/短いsignature、混在・名前/順序/bytes/headers、全読込失敗を確認した。変更した製品コードの実行行12/12・分岐6/6を実行し、除外0。製品全体の100%という意味ではない。

Linuxのsource重ね合わせによる関連4モジュール54件は成功・省略0。Black/isort/Flake8/Bandit0、差分・日本語説明・テキスト整合性とソースを確認した。最終commit由来の通常配布物、固定条件での実HTTP負荷、CIは別に記録する。前候補やsource overlayの成功を、最終配布物で実行した結果とは扱わない。

Windowsの既存`CharacterImageAppendOrderTests`の後片付け2件は、変更前の親候補でも同じ失敗を再現した。今回の変更で成功したとは報告しない。Linuxの既存検証と区別して保持する。

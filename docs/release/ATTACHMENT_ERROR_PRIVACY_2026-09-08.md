# 添付アップロードの内部エラー情報保護

## 問題と修正

アップロード処理は予期しない例外も文字列化して400応答に含めていた。保存先のパスやDBエラーなどの内部情報が利用者へ返る可能性があり、サーバー障害も入力ミスと区別できなかった。

入力のValidationErrorは従来どおり400、アプリの権限不足は403とし、それ以外は詳細を含まない日本語の500応答に変更した。調査用の例外はサーバーログに記録する。ログには内部情報が含まれ得るため、運用時の閲覧権限・保持管理が必要である。

アプリの権限不足にはPermissionErrorを継承した専用例外を導入した。これにより、保存先のOS PermissionErrorをアプリの権限エラーと誤認して公開する経路も防いだ。削除APIも専用例外だけを利用者向けの403に変換する。認可条件そのものは変更しない。

## 検証

- 修正前、OSError・RuntimeErrorの2ケースで期待する安全な500応答にならず失敗。初回修正後の追加検証でOS PermissionErrorの問題も再現してから修正。
- `schedules.test_attachment_error_privacy schedules.test_handout_attachments schedules.test_handout_download_access`: 26件成功。通常のアップロードと秘匿ファイルの取得拒否を含む。
- 追加したサービス/APIの権限ケースを含む `schedules.test_attachment_error_privacy`: 最終7件成功。内部3例外の応答本文に例外文字列がなく、調査ログが記録されることを確認。
- SQLiteのテストDBはテストランナーが作成・破棄。共有DBへの操作はない。
- カバレッジを上記実行で合算し、変更した実行行はすべて実行。2モジュール全体は94%であり、全体100%とはしない。Git管理外のデータは `tmp/attachment-error-coverage`。
- Black・isort・Flake8・差分検査に成功。Banditで実装2ファイルのHigh/Medium/Lowは0件。
- 日本語応答と実差分を自己レビューし、追加の指摘なし。画面構成は変更していないためブラウザ全体は再実行していない。

## 影響と残作業

サーバー障害時のHTTPステータスは400から500になる。DBスキーマ、保存形式、外部サービス設定、Secrets、費用は変更なし。実S3での障害注入・共有環境への配備は未実施。最終候補のCIと配備後検証は別途確認する。

復旧は本変更のコミットをrevertして再配備できるが、内部情報を応答する問題も復帰するため、原則として修正を維持した追加対応を行う。

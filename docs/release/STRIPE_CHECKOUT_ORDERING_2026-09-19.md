# 購入完了通知の順序変動・同時処理

## 修正

古いCheckout完了通知が新契約のIDを上書きする問題と、展開済みSubscriptionを含む通知が解約前のactive状態を復活させる問題を修正した。顧客不一致を拒否しない問題も含め、最初の3回帰テストで修正前の失敗を確認した。

購入完了処理全体をトランザクションにし、購読レコードをロックしてからStripeの最新Subscriptionを照会する。通知に含まれる顧客・購読ID、アプリに保存した顧客、照会結果のIDと顧客を照合する。現在保存している契約とは別の契約で、既にcanceledまたはincomplete_expiredの場合は上書きしない。照会失敗や不一致はロールバックし、Webhookの既存再送処理に委ねる。

展開済みの通知でも最新照会が必須になったため、オフラインsmokeのAPI境界を明示的なモックに変更した。実際のAPIを省略する本番用の例外は追加していない。

Stripeは通知順を保証せず、最新リソースの照会が可能であることを公式資料で確認した。[Webhook](https://docs.stripe.com/webhooks)、[Checkout Session](https://docs.stripe.com/api/checkout/sessions/object)を参照。

## 検証結果

- 課金関連196テスト成功（4.376秒）。古い契約、展開済み通知、所有者不一致、API一時失敗と再試行、欠損参照、削除済み利用者、metadataによる新契約の紐付けを確認した。
- 使い捨てPostgreSQL 18.3で14テスト成功（2.924秒）。2つのDB接続から同じ契約の購入完了を同時に処理し、権限付与の監査が1件であることを確認。既存の同時購入・請求・異議申し立てテストも含む。
- coverageで変更関数の未実行行は0。ただし、全分岐・実運用の網羅を意味しない。
- 実サンドボックスの既存の解約済みSubscriptionを読み取り、合成した古いactive通知を渡しても解約済みのままとなった。また、ローカルに新契約を模した記録がある場合は古い契約で上書きしなかった。2項目成功。[証跡](STRIPE_CHECKOUT_ORDER_API_2026-09-19.json)。署名付きCheckout通知からの実サービスE2Eではなく、新契約の記録はローカルのfixtureである。
- Black/isort、flake8、Bandit、差分検査に合格。利用者向け文言の変更はない。ソースレビューで今回の差分に残る修正必須事項は認めなかった。

実API操作は既存サンドボックス資源の読み取りのみ。実課金・メール送信・契約変更は行っていない。ローカル試験DBを破棄し、専用PostgreSQLコンテナを停止した。

## 未完了と反映条件

署名付きCheckoutと解約の実サービス通知を意図的に競合させるE2E、メール配送保証、AWS上の接続確認が残る。既に複数の非終了契約が存在する異常状態の自動整理は行わない。前コミットaa30265fのCIは確認時点で実行中であり、この変更のCI成功を証明しない。

追加のDBマイグレーションはない。main/AWS・Secrets・料金・税設定・継続費用に変更なし。Stripe Taxは未設定のままで、正式公開判定は引き続きNo-Go。同じ候補に含まれる0065・0066の共有DB適用は別途必要。切戻しは本変更のrevertで可能だが、通知順により権限を誤更新するため課金機能を止めて判断する。

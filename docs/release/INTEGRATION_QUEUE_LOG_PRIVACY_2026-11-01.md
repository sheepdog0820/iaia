# 外部連携のキュー登録失敗ログを保護

Google Calendar・Google Sheets・Discord通知のキュー登録に失敗した場合、アプリが例外本文とtracebackをログへ出す不備を修正する。brokerの資格情報、出力先や送信内容を含む例外が発生すると、情報をログへ残す可能性があった。

これはローカルの合成エラーで再現したコード上の問題であり、稼働AWSでの情報流出を観測した記録ではない。

## 変更と利用者への影響

`schedules/tasks.py`の3つのキュー登録関数で、例外情報を添えずに固定のサービス別エラーメッセージだけを記録する。ERRORの重要度、登録失敗時の`False`、既存の利用者向け日本語案内、再試行条件は維持する。成功時に渡す引数とCelery task IDの保存も変えない。

キューへの送信後にtask IDのDB保存が失敗する経路も、同じ固定ログで扱う。送信後の保存障害から「未送信だった」と判断できるようにする修正ではない。既存の再試行や外部サービス側の重複防止を変更しない。

例外本文・tracebackをこのログに残さないため、切り分けは固定したサービス名、時刻、既存ジョブ状態と、資格情報や業務内容を出さないインフラ側の監視で行う。

## 検証

- 実装前に3経路の送信失敗とGoogleのID保存失敗を合成エラーで再現し、整形済みログに合成の秘密マーカーが含まれることを確認した。初回のfixture不足による失敗とは分けて、製品不備によるREDを記録した。
- 追加5テストが成功し、上記の失敗時に秘密マーカー・例外情報・stack情報を記録しないこと、失敗の戻り値、成功時の引数・task ID保存を確認した。
- 関連する外部連携API・非同期ジョブ・Discord/HO公開・Calendar配送・Sheets配送/出力先の7モジュールを使い捨てSQLite DBで実行し、84件成功・省略0。今回変更した製品の3実行文を3件とも実行した。
- 対象差分のBlack/isort/Flake8/Bandit、UTF-8/LF/no BOM、ソース・日本語説明と差分を確認した。画面や利用者向け文言は変更しない。

固定コミットのCI結果はPRで別に追跡し、ローカル結果やmainの過去の成功を新候補のCI成功と読み替えない。

## 範囲・限界・復旧

DB/schema、権限、外部送信先、Secrets、IAM、料金や保存方針を変更しない。試験はmockと合成データだけを使い、AWS資源・共有DB・実OAuth/Google/Discordの操作や外部通知は行わない。

この変更だけで[I04〜I06・Q04などの正式公開条件](FORMAL_RELEASE_ACCEPTANCE_MATRIX.md)や実配送、実環境の監査が合格したとはしない。既知OS52指摘と正式公開No-Goを維持する。別の承認待ちPR #56/#57や、5移行のAWSコピーリハーサルの承認対象を変えない。

mainマージ・AWS反映は別途承認が必要。未適用コードはrevert PRで戻せるが、戻すと今回の例外情報のログ保存が再導入される。DB逆移行や実データ操作は不要。

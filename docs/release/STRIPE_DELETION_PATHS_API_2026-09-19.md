# 削除API・管理画面と実Stripeの接続検証

修正候補 `6ff9a1f9b9fe965b2461de0694530d3e18ffda96` を、隔離SQLite DBと承認済みStripeサンドボックスで検証した。[結果JSON](STRIPE_DELETION_PATHS_API_2026-09-19.json)の23項目すべて成功。

通常ユーザーAPI、管理者API、Django管理画面の単件削除・一括削除の4経路ごとに、専用の顧客と試用契約を作成した。顧客・契約のlivemode=falseを照合し、アプリには顧客IDだけ保存して契約通知未反映の状態を再現した。

各経路への実際のDELETEまたは確認POSTは、Stripe側に契約が残っている間は利用者を削除せず、誤った管理画面の削除ログも作成しなかった。契約をサンドボックスで解約した後は、同じ入口から削除できた。一括削除では、契約利用者と同時選択した無料利用者も拒否時には残り、解約後の成功時に両方を削除できた。

レスポンスはDjango Client / APIClientで検証した。外部HTTP通信は実Stripe APIを使用しているが、管理画面をブラウザーで操作した試験ではない。署名付きWebhookの配送も実行せず、未反映状態を意図的に維持した。AWS、Stripeの本番モード、実ユーザーデータは対象外。

試用契約4件は解約済みであることを再取得した。試験DBには専用管理者だけが残ることを確認後、DBを破棄した。サンドボックスの顧客・契約履歴は試験履歴として残る。実課金・外部メール送信、Secrets・権限・継続費用の変更はない。

先行候補0f6b81feの[CI全6ジョブ成功](STRIPE_CI_0F6B81FE_2026-09-19.json)も確認した。ただし0f6b81feには削除経路の修正が含まれない。6ff9a1f9自身のCIと、新しいソースを含む配布コンテナの確認を必要条件として維持する。main・AWSは未変更で、正式公開判定は引き続きNo-Go。

# キャラクター画像の同時追加による上限超過

確認日: 2026-09-08。修正前のアプリ候補はbca01195。

## 問題と修正

画像が4枚あるキャラクターに2件を同時アップロードすると、両方が枚数確認を通り、両方が201で保存される不具合をPostgreSQL 18.3で再現した。6版・7版とも再現し、無料・有料共通の5枚上限を守れていなかった。

画像追加の処理をトランザクションで囲み、キャラクター台帳の行ロック取得後に所有者を再確認してから、枚数・容量の検証と画像保存を行う。同一キャラクターへの追加は順番に検証され、最後の1枠への同時追加は一方が201、もう一方が400となる。既存画像の削除や有料失効時の整理は行わない。

ロック対象は当該キャラクターの台帳1行であり、世代削除・作成側と台帳を先にロックする順序を合わせた。画像保存中もロックを保持するため、同一キャラクターへの追加には待ち時間が発生する。実S3の遅延を含む負荷とタイムアウトの測定は別途必要。

## 検証

- 新しい回帰テストは独立した2つのDB接続とAPIClientで同じキャラクターへ送信する。最初の検証後に待機を入れて旧実装の競合を露出させた。修正前は6版・7版とも期待する `[201, 400]` に対し `[201, 201]` で失敗。
- 修正後の2テストは省略なしで成功。保存後の5枚、メイン画像1枚、既存4枚のID・パス・内容保持を確認した。
- 画像モデル・追加・編集・削除・ZIP取得・閲覧権限を含む関連3モジュールをPostgreSQLで実行し、43件成功。Black・isort・flake8も対象2ファイルで成功。差分と日本語エラー表示の保持をレビューした。
- SQLiteでは行ロックを実証できないため、回帰テストはPostgreSQL CIの明示的な実行一覧にも追加した。
- 隔離PostgreSQL 18.3の空のテストDBと一時MEDIA_ROOTを使用。通常本番イメージbca01195に対象ソースを読み取り専用でマウントした局所検証であり、新しい配布イメージの検証ではない。
- ローカル証跡は `tmp/image-concurrency-probe/red.log`、`captured.log`、`run.py`。試験用コンテナ・ネットワークは所有ラベル確認後に削除済み。

## 残る条件と影響

既存のHTTP負荷プローブは1キャラクターに正常サイズ6件を送り全件成功を期待していたため、後続の[試験修正](IMAGE_UPLOAD_PROBE_2026-09-08.md)でサイズ・形式ごとのキャラクターを分けた。修正後のHTTP27件は期待どおりだが、本修正のAPI回帰テストや少数のHTTP試験を、アップロード性能の合格判定に代用しない。

共有環境は未反映。DBマイグレーション、実データ変更、Secrets・権限変更、継続費用の増加はない。取り消す場合は本修正コミットを作業ブランチでrevertできるが、上限超過の競合が戻るため正式公開候補としては採用しない。

# 作成・編集APIの隔離環境性能試験

## 結果と範囲

2026-09-10、通常配布イメージ7b196988で登録100人・同時10フローを実行した。各人がシナリオ、セッション、6版キャラクター、7版キャラクターの順に、作成→名前/タイトル編集→再取得を実行する。計1,200リクエストすべてで期待したHTTP状態と名前/タイトルの一致を確認し、エラーは0件。各操作100件のp95はいずれも3秒以内だった。

| 対象 | 作成p95秒 | 編集p95秒 | 再取得p95秒 |
| --- | ---: | ---: | ---: |
| シナリオ | 1.400 | 1.390 | 1.297 |
| セッション | 2.504 | 2.006 | 1.707 |
| 6版キャラクター | 1.596 | 1.793 | 1.405 |
| 7版キャラクター | 1.521 | 1.605 | 1.490 |

POSTは400件すべて201、PATCHとGETは各400件すべて200。全リクエストの最大値はセッション作成の2.982秒。これは今回の入力・ローカル構成での1回の測定結果であり、通常操作全体や実AWSでの性能合格を証明しない。

## 条件と照合

- [一覧API再測定](READ_API_OPTIMIZED_RUNTIME_2026-09-10.md)と同じ通常イメージ `aws-pre-7b196988`、ID `sha256:e206c02ffe3b2422236e30a9f74dfee938297903bfb32a54ae2bd9e278e1a9ac`。アプリソースの後付けマウントなし。
- 内部Dockerネットワーク、アプリ0.25 CPU/512 MiB、PostgreSQL18.3 2 CPU/1 GiB、Redis7 128 MiB。新規一時DBにユーザー100人、グループ100件、キャラクター・セッション・シナリオ各1,000件を準備した。
- 100人それぞれのToken認証を使用し、ThreadPoolExecutorの同時フロー数を10に制限。各フローの12要求は直列で、人間の操作待ち時間は挟まない。HTTP要求開始からJSON受信までを計測し、nearest-rankでp95を算出した。
- 非公開シナリオとグループなしの非公開セッションを作成。キャラクターは年齢30、全能力値を6版10/7版50、7版の幸運50として作成した。技能・装備・画像の追加は含まない。
- 作成応答のIDを用いて名前/タイトルに「編集」を付けてPATCHし、GETで同じ値が返ることを確認。全フィールドの保存や他者からの閲覧拒否をこの試験で証明したわけではない。
- 全処理終了0。所有ラベルを照合したうえで試験用コンテナと内部ネットワークを削除し、残存なしを確認。実データ、AWS設定、権限、継続費用は変更していない。

## 無効な初回試験との区別

初回は試験データの7版必須項目「幸運」が欠け、各ユーザーの7版作成が400で拒否された。既存APIテストでもこの項目は必須であり、アプリの不具合修正は行っていない。初回の測定器は途中失敗したフローの測定値を集計できなかったため、この試行を性能評価には使用しない。試験データを修正し、途中で失敗しても取得済みの測定値を保持するよう測定器を直したうえで、新しい一時DBから上記試験を実施した。

証跡はGit管理外の `tmp/write-performance-7b196988/`。run.py、seed.py、check.py、write_probe.py、write-results.json、writes.log、fixture-requests.log、server.logを保存。初回結果はinvalid-fixture-results.jsonとinvalid-fixture-writes.logに分離した。使い捨て認証情報・envはコミットしない。

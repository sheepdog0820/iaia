# キャラクター画像の同時変更とメイン画像切替（2026-10-31）

## 修正する問題

同じキャラクターの別画像を同時にメインへ切り替えると、一方の要求が一意制約違反で500になる。6版・7版の専用`set_main/` APIと通常PATCHの両方で、修正前のコードを使った隔離PostgreSQL検査により再現した。DBの一意制約は維持されるが、正当な変更要求が正常に完了しない。

追加APIは従来からキャラクターのレジストリ行をロックする。一方、通常更新には同じトランザクションとロックがなく、専用切替は画像行だけを変更していた。このため、別要求によるメイン画像変更を反映する前に、以前の状態を基準とした変更が競合する。

## 変更と影響

`CharacterImageViewSet`の追加・PUT/PATCH・削除・並べ替え・メイン切替が、同じキャラクターレジストリ行のロックをトランザクション内で共有する。ロック取得後に所有者と版別データを読み直し、待機中に所有者が変わった要求は403で拒否する。

異なるキャラクターの操作は同じ行をロックしない。既存の画像5枚上限、版別テーブル、一意制約、閲覧権限、URLと応答形式は維持する。DB/schemaやマイグレーションの追加はない。キャラクター単位の待機が増えるため、この候補での性能は別途確認が必要で、先行候補d664bb40の測定値を本修正の測定値としない。

DBトランザクションはストレージ削除との分散トランザクションではない。S3/DB間の障害復旧、実規模の性能、SQLiteでの行ロックによる並行制御を証明する変更ではない。

## 検証

修正前は、固定した親コミットのビューを検査用に読み取りで重ね、4つの再現テストがすべて500を検出した。最初の試行にはテストURLの誤り等があったため採用せず、訂正後の実行を根拠とする。DB処理はモックしていない。

修正後の本番設定・隔離PostgreSQLでは、同時切替4件、追加の上限競合2件、全5種類の変更要求で待機中の所有権変更を検出する2件・10サブケースが成功した。CIと同じカバレッジ無効設定の関連PostgreSQL pytestは54件・12サブケース成功、CIと同じ5パッケージの行カバレッジを取るSQLite pytestは46件・2サブケース成功・PG専用8件省略。Django標準ランナーでもPostgreSQL54件成功。変更した実行可能行15行はすべて実行され、除外は追加していない。通常配布物内の検証結果はPRへ記録する。検査用の設定・合成データ・実行ログはGitへ含めない。

初期の関連テスト実行では、読み取り専用のmedia保存先で失敗した。また、このビューだけの分岐カバレッジを取る設定でDB接続切断が再現し、修正前の親コードでも同じ38件が失敗した。接続終了の記録を加えた検査と、上記のCIに合わせた設定では成功した。限定カバレッジ設定の失敗と全試行のログを保持し、ツール内部の根本原因を確定したとは扱わない。製品の接続設定や受け入れ条件を変更して回避していない。

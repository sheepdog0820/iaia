# 世代作成時の重複走査とロック待ちの改善

## 観測した問題

候補46530ebcを0.25vCPU/512MiBに制限し、専用PostgreSQL 18.3（2vCPU/1GiB）とinternal Dockerネットワークで測定した。利用者10人の独立した系譜、同じ版の10件または1,000件を合成データで用意し、モデルの世代作成と元世代削除を1件ずつ/10件同時で実行。外部接続・公開ポート・実データは使っていない。

旧候補では6版1,000件・10件同時作成が中央値9.961秒/最大12.713秒、10件中3件失敗。試験用に設定したlock_timeout=10秒、statement_timeout=30秒の条件であり、本番HTTPの障害率とは区別する。診断用の別実行でも10件中1件がSQLSTATE 55P03で失敗し、ロック待ちが原因であることを確認した（中央値9.466秒/最大15.050秒）。旧候補の7版測定は失敗時に止めたため比較値はない。

## 修正内容

CharacterVersionServiceは版別の全レコードをロックした後、最新の版番号を選ぶために各レコードの所属系譜を判定する。その判定のたびに全レコードから親IDの辞書を再作成していた。1,000件の独立した起点を判定する回帰テストでは1,001,000回の主キー参照となり、走査回数の上限検査が失敗した。

親ID辞書を1操作で一度だけ作り、同じ辞書を全判定に渡すよう修正。最新番号の選択を `_latest_version_for_root` にまとめた。1,000件の上記条件では主キー参照が2,000回になる。分岐した系譜の最大番号・別起点の除外を検証した。レジストリ→版別データのロック順、全体をロックする範囲、親の再取得、後続世代を残す削除処理は変更していない。

## 回帰検証とレビュー

PostgreSQL 18.3で、世代削除・6版世代作成・履歴一覧・新しい選択ロジックの27テストが成功（26.011秒、省略なし）。削除と作成の並行操作、後続データ保持、他者の操作拒否の既存検査を含む。専用コンテナ・DB・networkは所有ラベルを照合して削除した。

新しい選択ロジックの2テストをカバレッジ付きでも実行し、新ヘルパーの行・分岐がすべて実行されたことを確認。最初のブラウザ用イメージにはcoverageがなく起動できなかったため、ローカルPythonでDBを使わない同じ2件を実行した。証跡はtmp/lineage-selection-coverage.json。27件の機能検証は別のPostgreSQL実行の結果であり、カバレッジ取得の失敗を成功には数えない。

Black/isort/Flake8・差分・UTF-8/LF確認と自己レビューに問題なし。日本語UI文言の変更はない。変更後の全体CI・実環境への反映は未確認。

同じ版の別利用者を含めたロック待ちはなお起こり得る。深い系譜の走査、さらに大きい件数、実サービスのp95や許容エラー率は別途の性能条件と測定が必要。今回の改善を正式公開の性能ゲート完了とはせず、RDS復元承認待ち・Stripe保留も維持する。DB構造・共有データ・Secrets・権限・料金への変更はない。復旧はこのサービスの変更を戻すが、重複走査の遅延は再発する。

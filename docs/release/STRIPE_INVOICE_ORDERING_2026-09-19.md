# 支払い通知の順序逆転と請求別状態

## 問題と修正

旧Webhookは通知の到着順で利用者の支払い警告を上書きしていた。支払済みの請求に古い失敗通知が届くと警告とメールが再発し、別の請求の成功通知で未払いの警告を消せた。失敗通知が別イベントIDで再送されると同じ請求についてメールを繰り返した。

4件の失敗テストで再現し、請求IDごとの状態を `StripeInvoiceState` に保持する処理へ変更した。購読行をロックしてからStripeの現在のInvoiceを読み、IDと顧客を照合する。paid/voidで当該請求の失敗を解除し、他に失敗中の請求が残る限り利用者の警告を保持する。同じ請求の失敗が継続している間はメールを再送しない。権限の付与・停止は従来の購読処理が担当し、この処理は変更しない。

初回同期では既存のpayment_failed監査履歴から請求IDを集め、実Stripe状態で再確認する。過去の警告があるのに請求IDを特定できない場合は、警告を解除せずWebhookをfailedにする。顧客不一致・想定外のInvoice状態・API障害もfailedとして再試行可能にし、部分的なDB更新を巻き戻す。

設計の根拠は [Stripeの通知順序](https://docs.stripe.com/webhooks#event-ordering)。通知順序を前提にせず、現在のリソースを照会して処理する。CLIのdocsプラグインは利用できなかったため公式ドキュメントを参照した。

## 検証

- 回帰10テスト：支払後の古い失敗、別請求の成功、重複失敗、API失敗後の再送、既存警告の引継ぎ、履歴不足の保持、顧客不一致/想定外状態、複数未払いの個別解消、誤って解除された警告の復元、未連携顧客の無視。最終の単独実行は10件成功（1.579秒）。coverage JSONで新規の2同期関数に未実行行がないことを照合した。全分岐・全サービスの100%を意味しない。
- 課金・法務・設定・権限連携の260テスト成功（26.372秒）。エラーを意図的に起こす試験の500ログは期待結果。
- 使い捨てPostgreSQL 18.3で11テスト成功（3.517秒）。新しい同時処理試験では、請求Aの失敗と請求Bの成功を別接続から同時実行してもAの警告を保持する。既存の二重購入防止・接続再開試験も通過。
- 実Stripeサンドボックス `acct_1UFA5iE2s31mT3or` で10項目成功。公式失敗用PaymentMethodによる実invoice.payment_failed通知を隔離受信器で保持し、成功用PaymentMethodで支払った後に、保持した本文・署名を通常Webhookへ渡した。HTTP 200、イベントsucceeded、請求状態paid、警告なし、payment_failed監査なしを確認。[秘匿情報を除いた証跡](STRIPE_INVOICE_ORDER_EVENTS_2026-09-19.json)を保存した。

実試験はこのworktreeのコードをassertして読み込み、使い捨てSQLite、メモリメール、localhostのHTTP受信器を使用した。実カード・実ユーザー・実メール送信はない。契約は最後に解約し、転送とHTTPサーバーを停止、使い捨てDBを破棄した。

Black/isort、flake8、Bandit、マイグレーション差分検査、文字コード・差分検査を実行した。請求一覧の網羅や実メール配送まで検証したという意味ではない。今回のコード変更後のCIは別途確認が必要。

## 適用・復旧・残る範囲

追加の `accounts/0066_stripe_invoice_states` は新規テーブルのみ。請求ID・状態・失敗フラグ・イベントIDを保存し、鍵・カード情報は保存しない。共有DBには未適用で、0065と合わせて適用承認が必要。実環境の旧警告に監査履歴があるかを事前に読み取り確認する。履歴不足は請求の照合と承認されたデータ修復が必要で、推測したIDや成功通知で解消しない。

Stripe API照会が請求イベントごとに増え、移行時は過去の失敗請求の件数分も照会する。API停止中は再送待ちとなる。旧版へ戻す場合は追加テーブルを保持し、課金を停止して誤った警告・通知を避ける。

メール送信とDBコミットをまとめた配送保証、複数返金/異議申し立てと他種Webhookの全競合、AWSの設定・画面・有料必須ゲートは未完了。invoice.voided等の追加イベント購読は今回変更しておらず、voidは購読済み支払イベントの照会時に観測した場合の処理のみ。正式公開のNo-Goを維持する。Stripe Tax・本番課金・料金・継続費用は変更していない。

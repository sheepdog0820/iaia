# Stripe購入の重複防止と通信失敗時の再試行

## 変更内容

購入ボタンを続けて押すと、従来は別々のCheckoutが作られ、両方を決済できた。顧客作成やCheckout作成の応答が失われた場合も、新しいリクエストで再作成していた。4件の回帰テストでこの動作を再現してから修正した。

- 顧客ごとのDB行ロックで購入要求を直列化する。Webhook到着前でもStripeの現在の契約を照会し、activeだけでなくpast_due、unpaid、incompleteなど終了していない契約の追加購入を止める。
- 顧客作成・Checkout作成のパラメーターとランダムなidempotency keyを、実API呼出しより前のトランザクションで保存する。応答が失われても同じパラメーターとキーで再試行する。
- 開いている同一条件のCheckoutは再利用する。月額・年額を切り替える場合、古いCheckoutの失効に成功してから新しいCheckoutを作る。旧実装による未追跡の購入画面も、新規作成前に失効させる。
- 完了済みのCheckoutは現在の契約が終了している場合だけ新規購入を許可する。APIの照会や失効が失敗した場合は購入を進めない。
- Stripeのキー保持期間を超える危険を避けるため、作成結果不明のまま23時間経過したリクエストは新規作成せず、問い合わせを案内する。

方針は [Stripeの冪等リクエスト](https://docs.stripe.com/api/idempotent_requests) と [Checkoutの失効API](https://docs.stripe.com/api/checkout/sessions/expire) に基づく。購入APIにはリクエスト全体のトランザクションを適用せず、事前に保存した依頼がネットワーク例外で巻き戻らないようにしている。

## 検証結果

- 課金・権限連携・法務・本番設定の249テスト成功（27.644秒）。追加12件で連打、応答不明の再送、プラン切替、失効失敗、契約中の追加購入、解約後の再購入、古い未解決リクエストなどを確認した。
- 使い捨てPostgreSQL 18.3で14テスト成功（1.285秒）。同時に初回購入を2件実行しても顧客作成・Checkout作成が各1回になること、接続を閉じて再実行しても保存済みの依頼が残ることを確認した。API部分はモック。並行試験をPostgreSQL CI対象へ追加した。
- サンドボックスの実APIでも、顧客作成成功直後・Checkout作成成功直後に意図的に応答を失わせて再試行した。元の顧客ID・Checkout IDが返り、重複は生じなかった。連打で同じCheckout、プラン切替で旧Checkoutがexpired、開いているCheckoutは1件、作られたCheckoutは合計2件であることを確認した。7項目成功。決済は行わず、2件とも最後に失効させた。

実APIの記録は [再送検証の証跡](STRIPE_CHECKOUT_RETRY_EVENTS_2026-09-13.json) を参照。秘密鍵・顧客メール・Checkout URLは含まない。

## DB・運用への影響

`accounts/0065_stripe_billing_requests.py` は `StripeBillingRequest` テーブルの追加のみ。既存利用者や購読の値は変更しない。顧客作成時のプロフィールのスナップショット、購入条件、キー、StripeのリソースIDを保持する。API秘密鍵・カード情報は保存しない。名前とメールは既存プロフィールと同等の個人情報として扱い、管理画面や公開APIには露出させていない。

共有開発AWSにはこのマイグレーションを適用していない。適用時は対象版・DB変更・戻し方を含む承認が必要。コードを戻す場合もこの追加テーブルを残してよいが、購入機能を無効化してから旧版へ戻す。リクエスト行の削除・キー変更を通常の復旧方法にしない。作成結果不明の依頼はStripe側の履歴・顧客・Checkoutを照合してから復旧する。

Stripe APIの照会が購入開始時に増える。外部API待ち中は同一顧客の行ロックを保持するため、障害時には購入が待機または失敗する。今回は無料機能・料金・権限仕様・継続費用を変更していない。

この検証はWebhookの全イベント種別間の並行更新を保証するものではない。請求・異議申し立てをまたぐ通知順序、解約後の異議申し立て勝訴、AWS上の実接続・画面・運用メール・法務条件は引き続き残る。

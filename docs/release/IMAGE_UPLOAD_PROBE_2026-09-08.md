# 画像アップロード試験の現行上限への対応

確認日: 2026-09-08。

## 修正理由

`tests/performance/image_upload_load.py` は、同じキャラクターへ正常サイズの画像6件を送り、すべて201を期待していた。現在の5枚上限ではサイズ・形式の試験に枚数制限が混ざるため、サイズ・形式ごとに別のキャラクターを作成するよう変更した。9ケースの場合は9キャラクター・1シナリオ・1セッション・1グループを作成し、画像のPOSTは各種別9件、計27件となる。

シナリオとキャラクターを明示的に非公開とし、シナリオの版指定も現行のcoc6に統一した。リクエスト数・同時数・タイムアウトが0以下の場合はログインやデータ作成前に拒否する。枚数上限の競合は[独立した6版・7版の回帰テスト](CHARACTER_IMAGE_CONCURRENCY_2026-09-08.md)で扱い、このサイズ試験の期待ステータスを緩めて成功扱いにしない。

## 検証結果

- 単体テストは変更前に失敗を確認し、修正後2件・入力値3サブケースが成功。別々の9キャラクターへの送信、正常6件と超過3件の期待値、27件の送信数、非公開指定、不正条件でのログイン抑止を確認。
- ローカル内部ネットワークの実HTTPで最終変更を実行。同時数3、各ケース1件、合計27件が期待どおりに応答。JPEG/PNG/GIFの1 MiBと5 MiBは3種別で計18件が201、5 MiB+1 byteは計9件が400。終了コード0。
- 通常本番用イメージbca01195にe1ab21d0の画像ビューを読み取り専用でマウント。アプリ1 CPU/2 GiB、PostgreSQL 18.3は2 CPU/1 GiB、Redis 7は128 MiB。空のDB・合成ユーザー・使い捨て画像を使用し、試験後に所有ラベルを確認してコンテナ・ネットワークを削除した。
- 認証済みの試験用セッションを構成済みのRedisへ保存してクライアントに渡した。スクリプトのログイン処理自体は今回のHTTP検証対象ではない。内部HTTPのため試験クライアントだけでCookieのSecure属性を解除し、サーバー設定は変更していない。TLS・実OAuth・実ログインの証明にはしない。
- 初回は試験用セッションのDB/Redis不一致で401、修正後は内部HTTPでSecure Cookieが送信されず403となった。試験準備を修正した後の最終27件を成功記録とし、準備段階の失敗を画像APIの成否へ混ぜていない。
- Black・isort・flake8、差分と日本語文書の確認に成功。証跡は `tmp/image-http-probe/http-results.log` と同ディレクトリの試験用ランナー。秘密情報を含む使い捨てセッションファイルはGitへ含めない。

## 利用条件と残る検証

このスクリプトは試験データを作成し、自動削除しない。使い捨て環境か、作成対象と後片付けが承認された環境で実行する。今回は使い捨て環境全体を削除しており、共有環境のデータ変更・費用・権限変更はない。

生成画像は128×128の画像にゼロバイトを追加して送信サイズを調整している。転送サイズの境界確認であり、高解像度画像のデコード負荷・メモリ消費・実S3性能を証明しない。ケースごと1件のため表示されるp95も性能合格判定には使用しない。既定の9件を増やす場合は、シナリオ/セッション側の総容量等の制限との干渉も別途設計する。

実S3、合意したデータ量・同時利用・応答時間の閾値、長時間負荷、保存後の全画像再取得は残る。正式公開の性能条件Q02は未完了。変更は試験コードと文書のみで、取り消してもアプリの画像上限修正は維持される。

# 背景ワーカーの起動結果が不確定な場合の入力保持（2026-10-28）

PR #25の59543b94を基点に、既知3e5d46ee・30bc0830・b3496898から、同じ起動結果判定の修正を段階的に分離する。先行PRは未マージで、main追加マージや実AWSの操作承認を先取りしない。

## 利用者への影響と方針

通信障害で応答が失われても、AWSでは既に起動している可能性がある。起動失敗と断定して入力を削除せず、PENDINGと状態URLを返して既存の状態確認を続ける。ジョブIDを`clientToken`として固定し、同じジョブのSDK再試行で重複起動を防ぐ。新しいアプリ側の自動起動ループは追加しない。

不確定なジョブは既存の有効ジョブ判定で重複投稿を拒否し、設定済みのタイムアウトまで保持する。利用者がすぐに新規起動できる保証に変更しない。設定不足・引数検査・最初の明確な権限拒否等は従来どおり失敗にして入力を片付ける。既に進行/完了/失敗/削除となった最新状態を尊重する。起動ログには例外本文を出さず、操作名・ジョブID・例外種別だけを残す。

最初の段階では、固定SDKの実際の署名・再試行・パーサーも、合成の認証情報と差し替えた送信処理で検証した。実ECS・S3には接続せず、実画像や実ユーザーデータは使っていない。入力保持、重複拒否、後からのワーカー完了、タイムアウト、所有者制限とno-storeも確認した。

再試行後の拒否は`RetryAttempts`も判定する。最後が4xxでも、それ以前の受理可能性があれば入力を保持する。SDKの標準/legacy再試行を実際に通し、同じrequest bodyとtokenを保つこと、最初の明確な拒否は失敗処理を維持することを確認した。元履歴のCI追加hunkには別の有料権限テストの文脈があり、そのまま適用できなかったため、製品差分を変えず今回のテストだけをCI対象へ加えた。

署名中断では最終応答の再試行メタデータ自体が得られないため、当該clientの`needs-retry.ecs.RunTask`で各試行の不確定性を観測する。登録は呼び出し終了時に成功/失敗とも解除する。最初の送信前の署名失敗や明確な拒否は従来の失敗処理とし、途中で受理可能性が生じた後の署名/認証中断や明示的な失敗応答は入力を保持する。SDKの標準/legacy再試行、request body/token不変、後からの完了、重複拒否、期限切れを実SDKで検証した。SDK更新時にはこの観測経路も再検証する。

3段階を合わせた最終差分は製品変更51/51実行文を実行した。Black/isort/Flake8/Bandit・差分検査が成功し、自己レビューで追加の対処事項なし。既存の失敗表示を保持し、新しい利用者向け文言は追加しない。

## 境界と復旧

DBスキーマ・依存・モデル・料金・保存期間に変更はない。AWS/ECS/S3・共有DB/実データ・Secrets/権限・費用・外部通知は変更しない。SDKの応答や署名を模擬した検証は、実AWSの受け入れ・性能・復旧の完了にはしない。

main追加マージは最終headと検証結果を示して別途承認を確認する。復旧はrevert PRだが、起動済みか不確定なジョブの入力削除が再発する。[正式公開条件](FORMAL_RELEASE_ACCEPTANCE_MATRIX.md)・OS50指摘・Twisted RC2とNo-Goを維持する。

# 課金失敗メールの永続キューと再試行

## 変更と理由

従来は支払失敗WebhookのDBトランザクション中にメールを送信していた。後続のDB更新が失敗すると、監査記録や支払失敗状態がロールバックされてもメールだけ届く。SMTP失敗時には再配送予定も残らなかった。2つの回帰テストで修正前の誤送信を再現した。

新しい `BillingEmailDelivery` に送信予定を保存し、失敗状態・監査と同時にコミットする。Webhookからメールは送らない。Celery beatの毎分タスクが、期限到来済みの最大25件を配送する。配送失敗はDBに保持し、60秒から最大1時間の間隔で再試行する。空のメールアドレスも未配送として保持する。受信済みの支払回復や、同じ請求の新しい失敗に置き換えられた古いメールは送らず取り消す。

購読レコードを先にロックしてから配送レコードをロックし、並行ワーカーの通常時の二重送信を防ぐ。SMTP接続のタイムアウトは10秒。保存するエラーは分類コードのみで、SMTP例外の宛先や認証情報は保存しない。配送本文・宛先もキューへ複製しない。送信済みとはSMTP/backendによる受理を意味し、受信箱への到達証明ではない。

## 検証証拠

- 課金・通知順序・本番設定の258テスト成功（26.900秒）。
- 使い捨てPostgreSQL 18.3で18テスト成功（3.828秒）。並行ワーカー2つで送信呼出し1回、配送記録sent、試行回数1を確認した。
- ローカルSMTPで、Webhook処理中は未送信、一時拒否451でpending、再試行予定のDB保存、DB接続を閉じて再接続後の再送成功、再実行でも重複なし、の5項目に合格。[証跡](BILLING_EMAIL_SMTP_2026-09-19.json)。localhostのみで通信し、外部宛には送信していない。初回の試験スクリプトはimportパス不足で起動失敗したため、正しい作業ブランチのパスを指定して再実行した。
- 送信無効時と定期処理未設定時に有料公開ゲートが通る問題も2テストで再現し、拒否するチェックを追加した。設定が存在することと、worker/beatが実際に稼働していることの証明は別である。
- 追加の削除競合・状態表示・公開ゲートを含む最終47テスト成功（1.080秒）。新規配送モジュールの実行行カバレッジ100%（49行）。全分岐・実環境の保証ではない。
- Black/isort・flake8・Bandit・差分と文字コード検査を実施。新規の管理コマンド説明・モデル表示・状態名は日本語。UI本文は変更していない。

試験DB・専用PostgreSQLコンテナ・SMTP受信器は後片付け済み。実ユーザー・共有DB・実SMTP・AWS設定は変更していない。

## 反映と運用手順

1. 対象コミットのCIと自己レビュー結果を確認する。
2. 共有DBへ0065・0066・0067を適用する操作を承認対象に含める。0067は新しいテーブルの作成のみで、過去の失敗監査から配送予定を自動生成しない。
3. 既存のCelery worker/beatとSMTPの稼働、送信元、受信を検証する。追加リソースや費用、外部への試験メールの宛先は具体化して承認を確認する。
4. 承認済みの環境で `BILLING_EMAIL_DELIVERY_ENABLED=True` を設定する。既定値はFalseであり、未設定ではメールは配送されない。有料Checkoutの公開ゲートはこれを拒否する。
5. `python manage.py dispatch_billing_emails --status` で送信せずに有効化状態・pending件数・期限到来件数・最古の作成時刻を確認する。期限到来のpendingが継続する場合はworker/beatとSMTPを調べる。実配送する手動コマンドは `python manage.py dispatch_billing_emails`。対象・宛先を確認し、送信権限の範囲内でのみ実施する。

アラームへの接続とAWS上の実配送・障害復旧試験は未完了。ローカルでの成功を本番到達保証として扱わない。SMTPが受理した直後にプロセスが停止し、sentのDBコミットが残らなければ再送時に重複し得る。SMTPとDBを単一トランザクションにできないため、完全なexactly-once保証はない。

切戻し時は配送設定をFalseにしてworkerの処理終了を確認し、課金公開を止める。未配送記録を保ったままコード切戻しを検討し、0067の逆マイグレーションでキューを削除しない。旧コードはWebhook中に直接送信するため、その再稼働にも送信承認が必要。正式公開判定は引き続きNo-Go。

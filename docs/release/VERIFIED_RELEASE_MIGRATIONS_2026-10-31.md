# 0065〜0069の検証付き適用コマンド

`apply_verified_release_migrations`は、accounts0065〜0069の5移行だけを一つのトランザクションで適用し、対象データと履歴を比較する運用コマンドである。既存の`apply_verified_skill_adjustments`の0065〜0068/0068限定の境界は変更しない。新しい移行ファイルや利用者向け機能は追加しない。

**この実装・隔離検証は共有環境への適用承認ではない。** 共有DB・実データへの実行、全writer停止、直前backup、専用AWS資源、配備・復旧は、固定した対象と操作の別途承認が必要である。正式公開No-Goと全25条件を維持する。

## 実行前提

| 条件 | コマンドによる確認 |
| --- | --- |
| 明示した操作 | `--apply`と`--mode billing-skills-ownership`。既定では適用しない |
| 固定接続先 | `--expected-host`、`--expected-database`がDjango設定と一致し、実際のDB名も一致する |
| 接続の保護 | PG18、実接続TLS、default/current READ ONLY、DEBUG/SQL詳細ログ無効、既存トランザクションなし |
| スキーマ | 解決済み検索対象がpublicのみで、一時スキーマのない新しい専用接続。対象列・型・NULL制約が歴史モデルと一致する |
| 計画 | 全appの未適用計画が順方向の0065、0066、0067、0068、0069に完全一致。部分適用・追加移行・未知履歴・適用済みなら拒否 |
| 所有者補完 | `--expected-group-count`、`--expected-owner-membership-create-count`、`--expected-owner-membership-promote-count`と実集計が一致する。非負の整数だけを受け入れる |
| データの前提 | 作成者不明/無効、孤立/重複/未知ロールの所属、技能合算の32bit整数超過、先行作成済みの新規テーブルを拒否 |
| 運用者の確認 | 非空の`--backup-reference`と`--confirm-writers-stopped`を要求する |

backup参照とwriter停止フラグは運用者の意図を示すだけであり、backup取得・復元成功、全writerの停止、人間承認の存在をコマンドが確認した証拠ではない。DB接続が0件に見える場合も、スケジュール・再試行・手動実行を含む全writer停止の代わりにしない。

このコマンドだけを通常のWeb taskへ渡して実行しない。専用taskの初期化処理で、DB_PASSWORDだけを注入し、Django初期化より前からTLS/READ ONLYと固定接続先を設定する必要がある。コマンドが開始時にREAD ONLYであることだけでは、先行するアプリ初期化が書き込まなかった証明にならない。固定image・初期化処理・実行controller・最新backupコピーのリハーサルは別の準備対象である。

## 適用と比較

外側のトランザクションに入った直後に、そのトランザクションだけREAD WRITEへ切り替える。ロック待ち2秒・各SQL10秒を設定し、履歴・利用者・グループ・所属・両版技能・既存課金2テーブルをSHARE ROW EXCLUSIVEでロックする。競合する書込みがあれば中止する。このロックも全システムのwriter停止を保証しない。

移行前後に次を確認し、差分があればトランザクションを取り消す。

- 両版技能の全列は、bonus_pointsを0、other_pointsを旧2値の和とした結果に一致する。総値・注記等を変えない。
- グループの全列は、owner_idがcreated_by_idとなる以外は変えない。利用者の全列も保持する。
- 既存所属はID・加入時刻・他の列を保持し、所有者のroleだけadminへ補う。新規所属は不足していた所有者の組だけで、roleはadminである。
- PremiumSubscriptionとPremiumAuditLogの全列を保持する。新設する課金3テーブルと所有権申請テーブルは空である。
- 既存の移行履歴はID・app/name・適用時刻・既存重複を含めて保持し、予定の5記録だけが加わる。最終の全app計画は空である。
- 対象の列・型・NULL制約は0069適用後のモデルに一致する。

業務行の全文をPython側へ取得せず、PostgreSQL内で全列のJSON表現をSHA256に変換して比較する。所属・所有者・履歴の照合に必要な内部ID・ロール等とhashは処理中のメモリだけで扱い、出力・保存しない。成功時は固定した移行名と件数だけを出力し、SQL・行本文・元の例外は表示しない。

比較対象は上記のテーブルであり、DB全体・S3・課金事業者・外部配送の整合性を検証した結果には広げない。切替前後のsnapshot・主要操作・外部連携・復旧確認は引き続き必要である。

## 失敗と再実行

通常の検証不一致・移行途中の例外では、DDL・行・履歴を外側のトランザクションで取り消す。PostgreSQLのsequence値は取り消し対象ではなく、失敗試行でIDの欠番が生じ得る。sequenceを戻す操作は行わない。

COMMIT時の応答消失等では適用結果が不明となることがあるため、例外だけを根拠に「必ず未適用」とせず、同じjobとDBの実履歴・スキーマ・内容を読み取りで照合する。自動再実行は行わない。既に適用済みの場合はこのコマンドも拒否する。

0069適用後に移譲・元作成者退会等が始まった場合、単純な逆移行や旧Webの再開は復旧にならない。[所有権移譲の復旧条件](GROUP_OWNERSHIP_TRANSFER_SPEC_2026-10-31.md#0069の適用と復旧条件)を守り、書込み停止・前進修正、または承認済みbackupの復元/切替を検討する。旧コードと0069を混在させない。

## 検証範囲

隔離TLS PG18の合成データで、非空の技能/課金/所属、所属追加/管理者化、補完0、既存重複履歴、引数・接続・計画・スキーマの不一致、実際の非TLS接続、別接続の書込みロック、移行後の故意のデータ/履歴/スキーマ破損と取り消しを試験する。CIのPGサービスにも使い捨ての証明書を設定し、実TLS接続を確認してから同じ試験を実行する。証明書・keyは使い捨てCIコンテナ内だけに作成し、共有環境やIAM/Secretsを変更しない。

実件数・カバレッジ・最終CI・配布物内検証は、その対象headの実行結果とPRに記載する。隔離検証の成功を、共有DBでの実行・0069を含むAWSコピーリハーサル・正式公開の合格として扱わない。

実装時の最終ソースでは、CIと同じPG56モジュールを本番設定・実TLS・隔離DBで実行し、804件・460 subtests成功、省略0。新コマンドの実行文146/146・分岐24/24でカバレッジ100%を確認した。CI/entrypointの静的試験26件と、使い捨てPG18.3でのTLS設定・実接続・コンテナ削除も成功した。これらのローカル結果と、GitHub上の最終headのCI・通常配布物内検証は区別して記録する。
